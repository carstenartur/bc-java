## Actual public API result

The primary workload is the real `HashToEllipticCurve.getInstance(profile, dst).hashToCurve(message)` call sequence, with 64 rotating deterministic 32-byte messages. JMH consumes the returned point; serialization and input construction are outside timing. The following are microseconds/op, mean +/- the reported 99.9% JMH interval.

Ratios are equal-profile geometric means of optimized/baseline. The complete factory-plus-hash workload uses **14.13% less time on Java 21 and 14.79% less on Java 25**. Factory-only savings are 46.58% and 46.25%. All six primary intervals and all six factory intervals favor the optimized version without overlap.

All six reused-hash intervals overlap. No steady-state hash optimization is claimed. The previous differently-named-class experiment's Java 21 reuse anomaly is not reproduced here, but this does not isolate its cause.

Allocated bytes/op are approximately 2.9-3.3% lower for factory-plus-hash and 19.9-24.0% lower for factory only; this is not a peak-memory or retained-heap claim.

## Scope and upstream candidate

This supports a small upstream initialization improvement for the tested public NIST profiles. It is not an improvement to already-initialized hash computation, JVM cold start, all message lengths, all curves, RSA, or cryptographic security. In particular, the public Curve25519 suite uses a different mapping and is not covered by this claim.

Minimal production-and-tests candidate: `3d56837c3fe6c4a30fc7639b806958649e143210`, branch `perf/hash2curve-constants-upstream`, fork PR https://github.com/carstenartur/bc-java/pull/2 .
